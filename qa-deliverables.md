# Login feature: QA deliverables

Generated by the QA Tester Assistant from `requirements.md`. Reviewed and owned by the tester.

## Exact messages

| Situation | Message |
|---|---|
| Successful login | Successfully logged in |
| Existing username, wrong or blank password | Failed login, username or password incorrect |
| Non-existent username | username does not exist, please create one |
| Device locked (30 minutes) | your account is locked, please try after 30 mins |

## Assumptions

| ID | Assumption |
|----|-----------|
| A1 | The failure message is shown when the username exists and the password is wrong or blank. The non-existent username message is shown only when the username does not exist. |
| A2 | Non-existent username attempts do not count toward the 3 failures (N2). |
| A3 | Failures with different existing usernames from the same device accumulate (N3). |
| A4 | The lock message appears on the 3rd failure itself (N5). |
| A5 | The 8-character limit is a maximum for both fields (N6). |
| A6 | The failure count resets when the 30-minute lock expires (N7). |
| A7 | While locked, the lock message takes priority over every other message (N7). |
| A8 | Chrome and Edge mean latest stable desktop versions. All tests run from one machine and one IP. |
| A9 | The 5-second display has a tolerance of about 1 second. |

## Execution notes

- Run Group 1 (TC01 to TC13) first, then Group 2 (TC14 to TC19).
- TC14, TC15 and TC16 are one chain using a single lock. TC17, TC18 and TC19 each need a fresh lock. Expect 2.5 to 3 hours for Group 2, mostly waiting.
- Before any test that records failures, make sure the failure count is 0 with a successful login.
- Record exact message text and take screenshots as evidence.
- If behavior differs from an assumption, log it as a question first, not a defect, until the requirement owner confirms.
- Session behavior (logout, refresh, back button, timeout) is out of scope.
